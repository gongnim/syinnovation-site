## 1. 한 문장으로

회사 내부 서비스에 들어오는 모든 요청을, **누구의 어떤 기기인지(인증서)** 와 **지금 상황이 수상하지 않은지(위치, 기기 상태, 행동)** 를 보고 **요청마다** 허용, 재인증, 거부 중 하나로 판정하는 제로트러스트 접근 제어.

- 정식 명칭: **Trust Gateway**. 예전 이름은 TrustIn Gateway(TIG)이고 SDS·코드에는 아직 남아 있지만, **대외 표기에서는 "TrustIn"을 쓰지 않는다**(2026-11-11 사용자 확인). 앱은 **Trust Auth**.
- **세 가지 쓰임 (사용자 확인, 2026-11-11)**
  1. **통합 인증** — KB국민카드·롯데카드·웰컴저축은행 인증 서비스에서 운영 중인 모바일 인증 기술. 금융사 앱에 SDK로 들어감
  2. **직원용** — AC (Access Control, 업무 접근 제어, 주력)
  3. **대고객용** — FPS (결제 부정거래, 권고형) + FDS 진단
- 세 쓰임이 같은 판단 엔진(ZTCC + OPA)과 같은 인증 기술을 공유.

## 2. 핵심 아이디어 세 가지

1. **폰 + PC 두 기기를 엮는다** — 폰 앱(TrustIn Auth)으로 본인을 확인하고, 그 확인을 근거로 PC에 짧은 수명의 인증서를 준다.
2. **인증서는 짧게, 검사는 계속** — PC 인증서는 12시간, 자동 갱신 없음(발급마다 사람 승인). 접속 중에도 요청마다 IP·위치·기기 상태·행동을 다시 평가.
3. **내부망은 밖에 열지 않는다** — 고객사 내부 에이전트가 게이트웨이로 **먼저 연결**(HTTP/2 역방향). 고객사 방화벽에 들어오는 구멍이 없다.

## 4. 사용자 한 명의 흐름

1. **폰 등록** — 회사 이메일 → 6자리 OTP → 폰 보안 칩에서 키 생성 → 통제 센터가 1회용 승인 토큰 발급 → CA가 인증서 3종 발급. 정품 앱 증명(App Attest / Play Integrity)과 **CSR 결속**(정품 앱이 승인한 키로만 발급), Android는 하드웨어 키 증명까지.
2. **PC 등록** — PC 화면 QR을 폰으로 찍고 Face ID 승인 → **회사 소유** PC 인증서(12시간).
3. **업무 시작(바인딩)** — 두 번째 QR + 폰 생체로 "지금 이 PC를 쓰는 사람"을 묶는다. 공용 PC도 사람 단위로 구분. 유휴 시간이 지나면 풀린다.
4. **접속** — 보안 브라우저 → PC 로컬 프록시 → 게이트웨이(mTLS) → 검사 → 내부 에이전트 → 사내 서비스. 앱은 게이트웨이가 서명해 넣은 신원 헤더로 사용자를 알아본다(재로그인 없음).
5. **수상하면** — 401 + 폰으로 푸시 → 무엇이 바뀌었는지 보고 Face ID 승인 → 재시도 통과(인증서 재발급 없음).
6. **심각하면** — 위험이 매우 높거나, 재인증 요구가 반복되거나, 기기 상태가 나빠지면 그 폰의 인증서를 폐기. 다음 요청부터 거부.

## 5. 판단 방식

- **두 곳에서 평가**: 게이트웨이는 PC 요청마다(그 인증서의 첫 요청 대비 IP·지문·위치 변화), 통제 센터는 폰이 상황을 보고할 때(인증 시점 대비).
- **Fast Path / Slow Path**: 같은 상황이 계속 정상이면 이전 판정 재사용, 아니면 전체 평가.
- **판단 엔진 4종**: 위험 점수(IP·위치·기기 지문), 사용자별 이상 행동 점수(평소 패턴 대비), 규칙 표(Zen), **모순 탐지**(예: 두 기기가 비현실적인 속도로 떨어져 있음, 발급 국가와 접속 국가 불일치).
- **판단 근거 설명**: 모순 목록과 신뢰 점수를 판정 원장에 남기고, 관리 콘솔 판정 상세 화면에서 "왜 막았나"를 관계 표와 문장으로 보여 준다(특허 청구항 4 구현).
- **PC·폰 동석 판정**: PC와 폰이 같은 곳에 있는지 확인(2026-10 중순 enforce 전환).
- **신뢰 출구 대역**: 회사 NAT 공인 IP 대역 안의 IP 변경은 변경으로 치지 않아 사무실 내 불필요한 재인증을 막음(테넌트 콘솔에서 등록, 폰 재인증 필요).
- **기본 차단 + 관찰 모드**: 정책은 명시 허용만 통과. 새 규칙은 observe(기록만)로 먼저 보고 enforce로 전환.
- **추가 방어(현재 관찰 모드 중심)**: 내장 WAF(OWASP CRS), 가상 패치, 응답 반출 검사(DLP), 세션 행동 관찰(과다 요청·대량 다운로드·업무 외 시간).
- **장애 시 기본은 막기(fail-closed)**.

## 7. FPS (결제 부정거래) 라인

- **실시간 거래 평가(권고형)**: PG사가 거래를 넘기면 위험도를 평가해 허용·추가 확인·거부를 **권고**. 실제 차단과 추가 인증 방법은 PG사가 결정(TrustIn이 최종 고객에게 OTP를 받지 않음). 가맹점은 전용 인증서 또는 API 키로 접속.
- **FDS 진단 엔진(tig-fps)**: 고객사 FDS의 거래·룰 발동 기록을 받아 **오탐, 미탐, 쓸모없는 룰, 겹치는 룰, 룰을 끄면 생길 변화, TrustGateway가 추가로 잡은 사기, 시간에 따른 성능 저하**를 분석하고 점수·등급과 개선 제안을 낸다. 실시간 차단이 아니라 배치 분석. 거래 ID는 가명화해 원문을 저장하지 않음.
- 고객 데이터 업로드·연동 API(P7)는 아직 미구현.
